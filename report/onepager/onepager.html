CredoScore | Explain it confidently

Beginner's viva guide - Gradient Boosting, XGBoost and Random Forest. Read page 1 for understanding, page 2 for implementation, and the final half-page for rapid answers.

Your 40-second introduction: "CredoScore is a learning project for loan-default risk. A user enters 12 applicant details. Three trained models - Gradient Boosting, XGBoost and Random Forest - each estimate default probability. The screen compares their recommendations; Gradient Boosting supplies the main risk slip, explanation and adjustable cutoff. I trained and evaluated the models offline, exported them as JSON, and built a Next.js interface with Python scoring APIs. It demonstrates the complete ML workflow; it is not ready for real bank lending."

1 | The ML vocabulary you actually need

Default means failing to repay as required. Classification predicts a class: here 0 = good credit and 1 = bad credit/default. Supervised learning learns from examples with known outcomes. A feature is an input; the target/label is the outcome. Training learns model rules; inference applies fixed learned rules to a new applicant.

A decision tree asks learned questions such as "loan amount < threshold?", follows branches, and ends at a leaf containing a number. These are statistical splits learned from data, not banking rules manually typed by us. An ensemble combines many trees. A parameter is learned; a hyperparameter is a setting chosen before training, such as tree depth or count.

Overfitting: remembering training patterns that fail on new data. Underfitting: a model too simple to capture useful patterns. Depth limits, smaller updates, sampling and validation control these risks; more trees alone do not guarantee better results.

2 | What the data contains

UCI German Credit: 1,000 historical applicants, 700 good and 300 bad, with 20 original attributes. It is a small, dated German-credit dataset, using Deutsche Marks (DM). The project retains 12 inputs:

Six numeric: age, years employed, monthly income, loan amount, repayment months, existing credits. Six categorical: job type, housing, loan purpose, credit history, checking-account status, savings status.

Preprocessing maps source codes into readable values. Employment buckets become representative years. Income is derived from loan amount, duration and the source instalment-rate bucket; it is not directly observed salary and inherits that bucket's uncertainty. Categories are one-hot encoded: separate 0/1 columns avoid pretending that housing types have a numeric order. Six numeric columns plus 31 indicators make the 37-number feature vector. Trees do not require standardising feature scales.

Personal-status/sex is excluded, but age and proxy variables remain: removing one attribute does not prove fairness. Missing or unknown user inputs are rejected, not silently guessed. No new applicant is stored or used to retrain the live model.

3 | Gradient Boosting: successive corrections

Idea: a sequence of small trees improves one shared prediction. It starts with a constant raw score; each next tree learns a correction in the direction that reduces a loss (a numerical penalty for wrong predictions). For binary classification this follows the negative gradient of log-loss. "Fixing previous mistakes" is the intuition; it is not just subtracting 0/1 labels.

Training steps: initialise score; calculate each example's current error direction; fit a shallow tree to that direction; add a small fraction of its prediction; repeat. The learning rate controls each step's size. Smaller steps can generalise better but need more trees.

raw score = starting score + sum of weighted tree outputs
probability = sigmoid(A x raw score + B)

Our implementation: scikit-learn GradientBoostingClassifier, 250 trees, depth 3, learning rate 0.05, subsample 0.8, minimum leaf size 20. Randomised search tried 40 parameter combinations. The server walks the exported trees, adds their leaf values and calibrates the margin. It is the primary model because of its measured ranking performance and usable explanation, not because boosting is always best.

4 | XGBoost: a regularised boosting implementation

Full name: Extreme Gradient Boosting. It is also a sequence of corrective trees, not an unrelated neural network. XGBoost uses first- and second-order loss information - the gradient gives the improvement direction and the Hessian describes curvature - to choose useful tree splits and leaf weights. Regularisation penalises unnecessary complexity; efficient split-finding makes training practical.

Training steps: calculate gradients/Hessians from current predictions; choose splits with sufficient improvement after penalties; estimate leaf corrections; shrink the update by the learning rate; repeat. It still needs validation and can overfit; the name "Extreme" does not mean automatically more accurate.

Our implementation: XGBoost classifier with 200 trees, depth 3, learning rate 0.05. scale_pos_weight = 700/300 gives the minority bad-credit class more training weight. Raw margins are Platt-calibrated. The export stores leaf corrections already multiplied by the learning rate, so its JSON runtime multiplier is 1.0; applying 0.05 again would be wrong.

Important real bug: XGBoost routes a split left on value < threshold; scikit-learn boosting uses <=. Reusing the wrong comparison misrouted boundary values. The custom walker now branches on model type; export also respects XGBoost's float32 thresholds. Parity checks compare its output against the fitted library model.

5 | Random Forest: diverse trees working together

The correct name is Random Forest, not "random trees." Bagging builds many trees separately on bootstrap samples (sampling rows with replacement). A random subset of features is considered at splits. This makes trees less alike; combining them reduces variance. Unlike boosting, later trees do not correct earlier trees sequentially.

Training steps: draw a bootstrap sample; grow a tree using random feature subsets; repeat for many trees; combine predictions. For our probability output, each leaf contains a class-probability estimate and the forest averages tree probabilities. Majority voting is the class-label intuition, but not the arithmetic used here.

Our implementation: scikit-learn RandomForestClassifier, 300 trees, maximum depth 6, balanced class weights. The exported scorer averages the leaf probabilities and applies a sigmoid calibrator fitted to that average. Its response includes probability, band, display score and recommendation, without a contribution list.

Why three? To compare different learned predictions and expose agreement/disagreement. The API does not average these three models into a fourth ensemble or take their majority vote. They use the same dataset/features, so agreement is not independent proof of correctness. Each model is already an ensemble internally.

Why not only logistic regression? It was the simpler baseline; trees capture nonlinear patterns and interactions. Four families were benchmarked: logistic regression, GB, XGBoost and RF. Why not deep learning? There is little data and a tabular problem; this project did not establish that a neural network would improve it.

7 | Training, evaluation and calibration

Stratified five-fold validation: divide the data into five groups, maintaining roughly the 70:30 label ratio. Train on four groups and predict the held-out group; rotate until every applicant has an out-of-fold (OOF) prediction. Candidate models use the same folds. The preprocessing pipeline is fitted within each training fold; it must not learn from the held-out group.

Calibration turns model scores into better probability estimates. Platt scaling fits a small logistic model: p = 1/(1 + exp(-(A*s+B))). GB/XGBoost use raw margin s (an unbounded log-odds score); RF uses its average raw probability. Sigmoid maps any real number to 0-1. Calibration is not a promise that a particular borrower will default.

Important evaluation limit: the base scores are OOF, but tuning used these folds, and the global calibrator is fitted and assessed on the same OOF pairs. These are development estimates, not a fully untouched external test. Nested validation or a separate calibration/test split would give stronger evidence.

After evaluation, each production model is refitted on all 1,000 rows and exported. The portfolio dashboard uses saved OOF results; it is not an independent live bank portfolio. Training is offline; clicking "Score" performs inference only.

8 | What "good performance" means

Calibrated OOF metricGBXGBRF
ROC-AUC (higher)0.79280.78690.7833
PR-AUC (higher)0.63440.62990.6329
Brier loss (lower)0.16010.16190.1646

ROC-AUC: how often a randomly selected bad-credit applicant ranks riskier than a good-credit applicant. About 0.79 means about 79% of such pairs, not 79% classification accuracy. 0.5 is random ranking; 1 is perfect ranking. PR-AUC summarises precision/recall across thresholds and is useful for the minority default class; random baseline here is about 0.30.

Brier: average squared probability error; smaller is better. Predicting 30% for everybody gives 0.21. KS: largest gap between the good/bad score distributions; GB is 0.4776. Accuracy can mislead: "always good" already gets 70%. Precision asks how many predicted defaults are real; recall asks how many actual defaults were detected. False negatives approve likely defaulters; false positives turn away good borrowers.

9 | Which code does what?

ml/train.py: clean data, encode, benchmark, tune, calibrate, refit and export. data/german_credit.csv: cleaned data. model/: three model JSONs plus portfolio.json. JSON records categories, tree features/thresholds/children/leaves, calibration coefficients and metadata; it contains learned rules, not an AI chat prompt.

api/predict.py: shared validation, feature vector, tree walkers and primary-model endpoint. api/predict-compare.py: load all three artifacts, validate/encode once, score each, return separate results. api/portfolio.py: aggregate data. components/assess/assess-form.tsx validates the form; lib/api.ts sends the comparison request; the workbench renders the result. Next.js/React/TypeScript build the interface; Tailwind styles it. Vercel hosts the site and Python functions.

10 | Walk through one request

  1. The user selects a preset or enters 12 values. Browser validation checks numeric ranges and the instalment rule; invalid fields show a message.
  2. POST /api/predict-compare sends JSON. The server independently verifies required fields, finite numeric types, ranges and allowed categories. It checks loan_amount / duration_months <= 4 * monthly_income. This is a coarse input sanity rule, not a real affordability assessment.
  3. The server builds the same 37 features in the training order, walks the three tree ensembles and applies each model's calibration coefficients.
  4. It returns probability, risk band, 300-850 display score and decision per model. GB/XGBoost also return contributions. HTTP 200 means success; invalid requests receive 400 with a field/message.
  5. The interface shows the primary GB slip and drivers, plus all three model results. The individual cutoff slider changes the GB recommendation locally; it does not retrain models or alter the applicant's probability.

Why no pandas/scikit-learn in production? They are used to train offline. Exported trees need only standard-library Python arithmetic at runtime. This makes the deployment lightweight, but model export must preserve library behaviour. Next.js still has frontend dependencies; "dependency-free" describes Python scoring, not the entire website.

11 | Probability, band, score and decision differ

PD is estimated probability of default; 0.20 means 20%, not guaranteed default or repayment. Bands: low below 15%, medium 15% to below 35%, high at least 35%. Display score: round(850 - 550*p); it is our custom inverted scale, not an official bureau/FICO score.

Decision with cutoff c: approve if p < 0.6c; approve with conditions if 0.6c <= p < c; review if c <= p < 1.6c; otherwise decline. At default c = 25%, boundaries are 15%, 25%, 40%. These are project policy rules, not learned classes or bank policy. A 20% applicant is medium-band, score 740 and approved with conditions. Band boundaries stay fixed when c moves.

Cost explorer: approving a bad borrower costs 5 units; declining a good one costs 1. Expected sample cost per applicant is (5*bad_approved + good_declined)/1000. Higher cutoff usually approves more people and permits more defaults. Portfolio outcomes use precomputed cutoffs 5%-60% in 5-point steps; the individual slider uses 1-point steps.

12 | Explain the waterfall correctly

The displayed GB chart starts from a baseline prediction. Tree-path changes are assigned to the split features (a Saabas/path-decomposition explanation), grouped back from one-hot columns to original fields, and rescaled into probability-point changes. Baseline plus contributions reconstructs the prediction before output rounding. A +5 percentage-point bar means 30% becomes 35%, not a 5% relative increase.

The API rounds displayed contributions, so tiny sum differences can remain. These are model explanations, not causal claims; they do not prove changing a person's income would cause that exact risk change. The live waterfall is not full SHAP. RF has no driver breakdown here; XGBoost contributes to the API response, but GB drives the visible waterfall and cutoff.

13 | Demo, tests and honest limits

Demo order: open Assess -> Strong file -> Score -> explain PD/decision -> Stretched file -> compare three models -> show drivers -> move cutoff -> clear age to show validation -> open portfolio/methodology. Values depend on the exact preset; never invent a result if the demo fails.

Recorded tests: 62 report cases across maths, API, UI and integration, including export parity, additivity, malformed input and three-model agreement. A real fix was XGBoost's strict split comparison. Tests support correctness; they do not prove fairness, causality or future accuracy. Limits: small/old sample, derived income, selection bias from recorded lending outcomes, no formal fairness/drift audit and no guarantee on new populations.

What did you build, rather than just train? "A complete path from historical data to three calibrated models, lightweight scoring APIs, validation, model comparison, explanations and a working interface." Open one source file and show its place in that path.

Why did you choose GB if XGBoost is famous? "We compared models on the same folds. Our calibrated GB AUC is slightly higher, and its explanation fits the primary interface. The small gap does not prove GB is universally superior." Untuned benchmark, tuning-search score and final calibrated metrics are different stages; quote the table on page 2.

What if the models disagree? "Display the disagreement; do not hide it or invent certainty. The current UI keeps GB as primary and shows the alternatives. Human review and further validation would be appropriate in a real deployment."

How do you avoid leakage? "Fit preprocessing/model only on the training fold. An OOF base prediction comes from a model that excluded that row. Our tuning/calibration still reuse validation data, so I would add nested validation or an untouched test set before claiming unbiased performance."

Did you use AI? "I used Claude Code/Codex to assist coding and debugging. Those are development tools, not the three prediction models. I can explain the pipeline, trace a request and demonstrate the recorded checks." Describe only work you actually did; do not claim you wrote every line unaided.

What happens when the API is unavailable? The form should show a readable error and retain the inputs. A preset fills the form; it is not a cached/fake model result. Portfolio/methodology can read exported aggregates without retraining.

Could the model be wrong or biased? Yes. Calibration concerns groups, not individual certainty. Shared-data agreement is not proof; excluding sex/marital status does not remove proxies. Use updated representative data, fairness checks, a separate test set and monitoring before considering real use.

What would you improve? Newer, larger data; stronger external/nested evaluation; fairness and drift monitoring; calibrated uncertainty; clearer explanations; batch scoring. These are future improvements, not already-built features.

If asked something you do not know: say "I have not implemented/measured that; I would check this function or run this test." Explain what you can verify instead of guessing numbers or calling every explanation SHAP.
